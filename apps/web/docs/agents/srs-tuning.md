# 복습 스케줄(SRS) 상수 조정 절차

간격 반복은 상수를 실측으로 조정해야 쓸 만해지는 알고리즘이다. `ease` 상한 2.5,
학습 단계 1·3일, 재확인 3시간, 연체 점수 상한 14일, leech 8회 — 전부 근거가 있는
값이지만 **이 서비스의 문항·사용자로 검증된 값은 아니다**. 근거 없이 만지면 몇 주
뒤에야 드러나는 방식으로 망가진다(사용자마다 복습일이 조용히 어긋나고, 화면에는
아무 표시도 안 난다).

그래서 상수를 건드리기 전에 반드시 이 절차를 거친다.

## 1. 실측을 먼저 본다

```
cd apps/web
npm run retention-report                 # 전체 기간
npm run retention-report -- --days 30    # 최근 30일
npm run retention-report -- --user <uuid>
npm run retention-report -- --simulate   # DB 없이 가상 학습자로 (표 모양 확인용)
```

실데이터가 없는 개발 단계에서는 `--simulate` 로 표 읽는 법만 익혀 두면 된다.
그 숫자로 상수를 정하면 안 된다 — 가상 학습자의 기억 모델은 가정이다.

`srs_reviews`(채점마다 남는 로그)를 간격 구간별 유지율로 접어 준다. 표의 각 열:

| 열 | 뜻 |
|---|---|
| 표본 | **예정일 이후에** 본 채점 수. 회독·섞어풀기가 끌어온 조기 채점은 뺐다 |
| 정답률 | 그중 정답 비율 (찍어서 맞힌 것 포함) |
| 회상추정 | 4지선다 찍기(25%)를 걷어낸 "실제로 기억하고 있었을 확률" |
| 권장 배수 | 목표 유지율 90%에 맞추려면 그 구간 간격에 곱해야 하는 값 |
| 판정 | 표본 30 미만이면 판정하지 않는다 |

조기 채점을 표본에서 빼는 이유가 중요하다. 이 서비스의 기본 학습 방식은 회독이라
간격 62일짜리를 5일 만에 다시 만나는 일이 정상적으로 벌어진다. 그걸 유지율에 넣으면
회독을 열심히 하는 사용자일수록 "간격이 길다"는 잘못된 결론이 나온다.

## 2. 시뮬레이션으로 방향을 확인한다

```
cd packages/core
npm test                                  # simulate.test.ts 포함
```

`src/simulate.ts`는 문항마다 기억 안정도를 들고 있는 가상 학습자를 실제 앱과 같은
함수(`nextSrs`·`buildDueQueue`)로 몇 달치 굴린다. 상수를 바꿔 보고 유지율·적체·편중이
어느 쪽으로 움직이는지 볼 수 있다. 실측과 **같은 집계 함수**(`srs-retention.ts`)를
쓰므로 두 표를 나란히 놓고 비교하면 된다.

단, 시뮬레이션의 절대값은 가상 학습자 모델의 가정에 딸린 값이다. 믿을 수 있는 건
구조적 성질(적체가 쌓이는가, 큐가 비는가, 한 시험지가 도배하는가)과 변경 전후
비교이지, "유지율 43%" 같은 숫자 자체가 아니다. 그래서 시뮬레이션 테스트의 임계에도
유지율은 넣지 않았다.

## 3. 바꾼다면

- **정본은 `packages/core/src/srs.ts` 하나**. 고친 뒤 `npm run bundle-edge -w @gongmoa/core`
  로 `supabase/functions/_shared/core.mjs` 를 재생성해 같은 커밋에 넣는다(번들이 낡으면
  웹과 앱의 복습일이 조용히 어긋난다 — `bundle-edge:check` 가 PR 을 막는다).
- 기존 사용자의 스케줄은 마이그레이션하지 않는다. 상수 변경은 다음 채점부터
  반영되고, 이미 배정된 `srs_due_at`은 그대로 남는다.
- `packages/core/src/srs.test.ts`에 근거를 케이스로 남긴다.

## 개념 축(keyword_title)

같은 개념이 하루 큐를 도배하지 않게 `question_explanations.keyword_title` 에서
그룹 키를 뽑아 쓴다(`packages/core/src/concept-key.ts`).

`keyword_title` 은 통제 어휘가 아니라 해설 배치가 매번 자유롭게 쓴 문자열이라
("대칭키 암호" / "대칭키 암호화 방식" / "대칭키 암호 개념"), 정밀하게 통일하지 않고
**제목의 첫 의미 토큰**으로 거칠게 묶는다. 이 용도에서는 양쪽 실패가 전부 싸기
때문이다 — 잘못 묶이면 그 문항이 하루 밀리고, 안 묶이면 지금과 같다.

커버리지·표기 분포가 궁금하면:

```sql
select keyword_title, count(*) from question_explanations
where keyword_title is not null
group by 1 order by 2 desc limit 30;
```

상위 개념이 여러 건씩 뭉쳐 있으면 그대로 잘 돈다. 전부 1건씩 흩어져 있으면
`concept-key.ts` 의 절단 규칙을 조절할 자리다(꼬리말 목록·파생 접미사).

정본 개념 사전(`concepts`)이 채워지면 큐는 자동으로 그쪽 축(`concept_id`)으로 옮겨
가고, 이 파일은 정본이 없는 문항의 폴백으로만 남는다. 사전 구축 절차는
`docs/agents/concept-dictionary.md`.

## 금지선

- **실측 표만 보고 상수를 한 번에 크게 바꾸지 말 것.** 구간당 100건 이상, 가능하면
  두 번 이상 같은 방향이 나오는지 확인한다. 표본이 얇은 구간의 권장 배수는 잡음이다.
- **`srs_reviews`에 클라이언트 쓰기 정책을 열지 말 것.** 이 로그로 상수를 정하므로
  사용자가 행을 넣을 수 있으면 근거가 오염된다. 쓰기는 서버 채점 경로(service_role)만
  한다.
- **유지율이 낮다고 `ease`부터 낮추지 말 것.** 학습 단계(1·3일)는 고정값이라 `ease`가
  닿지 않는다. 시뮬레이션에서 ease를 2.5 → 1.8로 낮춰도 1-2일·3-7일 구간 유지율은
  거의 안 움직였다. 그 구간이 문제면 손댈 곳은 학습 단계나 재확인 간격이다.
- **정밀 개념 분류가 필요하면 `concept-key.ts` 를 늘리지 말 것.** 약점 진단("대칭키가
  약합니다")처럼 사용자에게 개념을 말해주는 기능은 틀리면 안 되므로 통제 어휘 사전이
  있어야 한다. 이 파일은 큐 다양성 전용이고, 그 둘을 한 함수로 겸하려 들면 양쪽 다
  못 한다.
- 조기 채점(회독) 완화 규칙(`SRS_EARLY_LAPSE_RATIO`, `boundByElapsed`)을 지울 때는
  회독형 프로필 시뮬레이션을 먼저 돌릴 것. 이 규칙들이 없으면 회독을 성실히 할수록
  복습 큐가 미래로 비워진다.
