# 개념 사전 (keyword_title 정본화) 절차

`question_explanations.keyword_title` 은 해설 배치가 문항마다 자유롭게 쓴 문자열이다.
"대칭키 암호" / "대칭키 암호화 방식" / "대칭키 알고리즘"이 서로 다른 값으로 들어와
있다. 이걸 사람이 정리한 정본 개념 목록(`concepts`)으로 접는 작업이다.

## 왜 축이 둘인가

용도가 둘이고 **요구 입도가 반대**다. 하나의 평평한 목록으로 둘 다 하려 하면 실패한다.

| 용도 | 요구 | 쓰는 축 |
|---|---|---|
| 복습 큐 다양성 | 거칠어야 한다. 잘게 쪼개면 상한이 안 걸린다 | 단원(대분류) |
| 약점 진단 | 정밀 + **개념당 표본**이 있어야 한다 | 개념(소분류) |

"대칭키가 약합니다"를 말하려면 그 개념 문항을 서너 개는 틀렸어야 한다. 그래서
`concepts` 는 2단 계층이다 — `parent_id` 가 null 인 행이 단원, 그 자식이 개념.

## 입도는 감이 아니라 표본에서 역산한다

1. 사용자가 한 과목에서 틀리는 문항 수를 20~50으로 잡는다
2. 개념 하나를 "약하다"고 판정하려면 그중 3~5개가 그 개념이어야 한다
3. 즉 **과목당 개념 20~40개, 단원 5~10개**가 현실적인 상한이다
4. 코퍼스 기준 문항이 3개 미만인 개념은 세우지 말고 상위(단원)로 흡수한다

`npm run concept-inventory` 가 과목별로 이 목표치를 계산해서 같이 찍는다.

## 이름 짓기 규칙

1. **발문이 가리키는 대상**을 이름으로 쓴다. "대칭키 암호 알고리즘에 대한 설명으로
   옳지 않은 것은?" → `대칭키 암호`
   - 대비형 문항(선지가 공개키와 비교)이라고 `대칭키 vs 공개키` 를 새로 만들지 말 것.
     그러면 개념 수가 폭발하고, "이 문제의 진짜 주제가 뭘까"로 판단하면 사람마다
     답이 달라져 표기가 다시 흔들린다. 발문 기준은 누가 해도 같은 답이 나온다.
2. **문제 유형 꼬리말 금지** — `~의 특징`, `~에 대한 설명`, `~ 비교`, `~ 옳은 것`.
   문제마다 달라서 표기를 흩뜨린다
3. 명사구로. 조사·서술 없이
4. **과목 접두 금지** (`정보보호론 대칭키` ✗). `concepts.subject_id` 가 이미 안다
5. 연도·출처 금지 (`2021 국가직 대칭키` ✗)
6. 약어는 별칭으로. 정본은 풀어쓴 이름(`공개키 기반구조`, 별칭 `PKI`)

## 독해는 개념이 아니라 기능으로 묶는다

국어 비문학·영어 독해는 **지문이 재출제되지 않는다.** "조선 후기 상업의 발달"을
개념으로 세우면:

- 그 개념 문항은 코퍼스에 한둘 → 영원히 얇은 개념, 진단 표본이 0
- 사용자에게 "'조선 후기 상업'이 약합니다"는 **쓸모가 없다.** 그 지문 다시 안 나온다

그래서 **묻는 능력**으로 묶는다(`kind = "skill"`). 재출제되고, 표본이 넉넉하고,
"빈칸추론이 약합니다"가 말이 된다.

| 과목 | 기능형 개념 예시 |
|---|---|
| 국어 독해 | 중심내용 파악 · 세부내용 일치 · 추론 · 글의 전개 방식 · 문맥 어휘 · 자료 해석 |
| 영어 | 주제·제목 · 요지 · 빈칸추론 · 순서배열 · 문장삽입 · 무관한 문장 · 함의추론 · 어휘추론 |

**과목이 아니라 문항 성격으로 갈린다.** 국어에도 지식형이 많고(사동·피동, 음운변동,
한글맞춤법, 한자성어), 영어 어법(가정법, 관계사)도 지식형이다. 반대로 영어 어휘는
단어별로 세우면 수천 개가 되니 `문맥 어휘추론` 기능형 하나로 묶는다.

지문 주제는 **버리지 않는다.** `keyword_title` 에는 "조선 후기 상업의 발달"이 그대로
남아 오답노트에서 그 지문을 알아보는 데 쓰이고, `concept_id` 만 기능형으로 붙는다.
축을 둘로 분리해 둔 것이 여기서 값을 한다.

`kind` 로 갈리는 것 둘:

| | 지식형(knowledge) | 기능형(skill) |
|---|---|---|
| 진단 문구 | "이 개념을 모릅니다 — 개념 학습부터" | "이 유형에 약합니다 — 풀이 전략" |
| 최대 점유 상한 | 20% 초과면 입도가 거칠다 | 50%까지 정상 (영어 빈칸추론이 실제로 그렇다) |

## 절차

```
cd apps/web

# 1. 현황 — 여기서 방향이 갈린다. 보고 멈춰서 판단할 것
npm run concept-inventory
npm run concept-inventory -- --subject 정보보호론

# 2. 초안 뽑기(사람이 손볼 파일)
npm run concept-inventory -- --subject 정보보호론 --draft concepts.json

# 3. concepts.json 을 손으로 쪼개고 합친다 (아래 형식)

# 4. 등록·매핑 — 반드시 과목 하나씩, dry-run 먼저
npm run apply-concepts -- --file concepts.json --subject 정보보호론 --dry-run
npm run apply-concepts -- --file concepts.json --subject 정보보호론

# 5. 건강 검진. 통과 못 하면 3번으로 돌아간다
npm run concept-inventory -- --verify
```

초안 형식:

```json
{
  "정보보호론": [
    { "name": "대칭키 암호", "unit": "암호학",
      "aliases": ["대칭키 암호", "대칭키 암호화 방식", "대칭키 알고리즘"] },
    { "name": "공개키 기반구조", "unit": "암호학", "aliases": ["공개키 기반구조", "PKI"] }
  ],
  "영어": [
    { "name": "빈칸추론", "unit": "독해", "kind": "skill",
      "aliases": ["빈칸 추론", "빈칸 완성"] },
    { "name": "가정법", "unit": "어법", "aliases": ["가정법 과거", "가정법 과거완료"] }
  ]
}
```

`--draft` 산출물은 **확정이 아니다.** 묶는 기준이 "제목의 첫 의미 토큰"이라
"행정행위의 하자"와 "행정행위의 취소"가 한 묶음으로 나온다 — 큐 다양성에는 맞지만
진단 축으로는 쪼개야 한다. 그 판단이 이 작업의 본체다.

## 검진 기준 (`--verify`)

| 항목 | 기준 | 어긋나면 |
|---|---|---|
| 매핑 커버리지 | 95% 이상 | 별칭 보강 |
| 얇은 개념(3문항 미만) 비율 | 20% 이하 | 입도가 잘다 — 상위로 흡수 |
| 최대 개념 점유 | 지식형 20% · 기능형 50% 이하 | 입도가 거칠다 — 쪼갠다 |
| DB 백필 | 규칙과 일치 | `apply-concepts` 재실행 |

숫자가 다 통과해도 **개념당 문항 3개씩은 눈으로 확인할 것.** 개수만 맞다고 성공으로
판단하는 건 이 레포에서 이미 사고가 난 방식이다(AGENTS.md 크롭 항목).

## 코드가 이걸 어떻게 쓰나

- 복습 큐: `collectDueCandidates` 가 후보에 `conceptKey` 를 붙인다.
  **정본(`concept_id`)이 있으면 그걸 쓰고, 없으면** `packages/core/src/concept-key.ts`
  가 `keyword_title` 에서 뽑은 임시 키로 떨어진다. 사전이 채워질수록 정확한 축으로
  자연히 옮겨 간다.
- 매칭 규칙은 `packages/core/src/concept-dictionary.ts`(순수 계산, 테스트 있음).
  별칭이 1차, concept-key 그룹이 2차 그물이다. **한 그룹 키에 정본이 둘 이상 걸리면
  그 키로는 안 붙인다** — 찍어서 붙이면 진단이 조용히 틀린다.

## 금지선

- **`keyword_title` 원본 UPDATE 금지.** 화면에 그대로 보여주는 값이다. 정리 결과는
  `concept_id` 라는 별도 축으로만 붙인다.
- **개념 id 재발급 금지.** 이름은 바꿔도 되지만 id 가 바뀌면 진단의 시간축 이력이
  끊긴다. 없앨 때도 삭제가 아니라 `merged_into` 로 합친다.
- **전 과목 일괄 매핑 금지.** 과목 하나로 검증한 뒤 넘어간다.
- **미매칭을 "기타"로 뭉치지 말 것.** 뭉치는 순간 진단이 죽는다. 별칭으로 넣을지 새
  개념으로 세울지 사람이 판단한다.
- **별칭을 개념 사이로 옮기지 말 것.** `apply-concepts` 가 충돌을 보고하고 건너뛰게
  돼 있다. 강제로 옮기면 분포가 소리 없이 흔들리고 화면에는 아무 표시도 안 난다.
- **`concepts`/`concept_aliases` 에 클라이언트 쓰기 정책을 열지 말 것.** 진단의 근거가
  오염된다. 쓰기는 정리 스크립트(service_role)만.
- **독해 지문 주제를 개념으로 세우지 말 것.** 지문은 재출제되지 않아 표본이 안 나오고,
  사용자에게 해줄 말도 없다. `kind: "skill"` 로 묻는 능력을 세운다.
- **`concept-key.ts` 를 정밀 분류용으로 늘리지 말 것.** 그건 사전이 없을 때의
  폴백이고, 둘을 한 함수로 겸하려 들면 양쪽 다 못 한다.
