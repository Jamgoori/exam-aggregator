## 0. 현재 상태 요약 (출발점)

이미 갖춰진 것:

| 자산 | 위치 | 비고 |
|---|---|---|
| 문항 단위 정오 기록 | `cbt_attempts` + `cbt_attempt_answers` | 선택지·정오·응시별 전부 보존 |
| 오답 집계 로직 | `src/lib/wrong-notes.ts` | 틀린 횟수, "극복"(최근 응시에서 맞힘) 판정까지 계산 |
| 오답노트 UI | 마이페이지 탭 → 과목 → 문제지 드릴다운 | 문항 이미지·정답·AI 해설 표시 |
| 문항별 개념 키워드 | `question_explanations.keyword_title` | 해설 배치 루틴이 자동 축적 중 — **약점 진단의 핵심 재료** |
| 단원 태그 컬럼 | `questions.unit_tag` | 스키마에 "오답노트 단원별 분석용"으로 예약만 돼 있고 미사용 |
| CBT 솔버 | `cbt-solver.tsx` 일식 | 문제지 단위 풀이 전제 |
| 시간당 제한 패턴 | `explanation_access_log` | "일 1회" 제한 구현 시 참고 가능 |

핵심 한계: 모든 것이 **"문제지" 단위**로 묶여 있다. 과목 오답노트도 문제지 카드
목록이지 문항이 평평하게 모이지 않고, CBT도 문제지 하나만 풀 수 있다. 이번
로드맵의 본질은 **오답 데이터의 기본 단위를 문제지에서 "문항"으로 내리는 것**이다.

## Phase 1 — 과목별 틀린문제 모아보기 (기반 겸 첫 기능)

**목표**: 과목 오답노트를 "문제지 카드 목록"에서 "그 과목에서 틀린 문항 전체를
한 화면에 펼친 목록"으로 확장. 이후 모든 기능(섞어풀기·진단)의 데이터 통로가 된다.

### 만들 것
- 과목 오답노트에 뷰 전환: 기존 "문제지별" 탭 + 신규 **"문항 모아보기"** 탭.
- 필터/정렬: 미극복만 · 2번 이상 틀림 · 최근 틀린 순 · 자주 틀린 순 · 연도/급수.
- 문항 카드는 기존 `wrong-note-question-card.tsx` 재사용(출처 문제지 표시만 추가).
- (선택) 인쇄/PDF 내보내기 — 기존 `print-button`/`explanation-auto-print` 패턴 재사용.

### 데이터 작업
- `getSubjectWrongNoteOverview`는 현재 요약만 주므로, 과목 단위로 문항
  상세(이미지·정답·해설)까지 합치는 `getSubjectWrongNoteQuestions` 계열 추가.
  `fetchQuestionMedia`/`fetchCorrectAnswers`/`fetchExplanations`가 이미
  다중 paper를 받으므로 조합만 하면 된다.
- **성능 주의**: 회독이 쌓인 사용자는 문항 수가 수백 개가 될 수 있다.
  페이지네이션 또는 "미극복 우선 + 더보기"로 시작하고, 무거워지면 그때
  집계 테이블(Phase 2의 `user_question_status`)로 옮긴다. 처음부터 캐시 테이블을
  만들지 않는다 — 파생 데이터는 파생인 채로 시작하는 게 되돌리기 쉽다.

### 완료 기준
과목 페이지에서 필터 걸고 문항만 쭉 넘겨보는 흐름이 실제 회독 10회+ 계정에서
2초 안에 뜬다.

## Phase 2 — 섞어풀기 (오답 재풀이 CBT)

**목표**: 선택한 오답들을 무작위로 섞어 CBT로 다시 풀고, 그 결과가 오답노트의
"극복" 상태에 반영되게 한다. 이 Phase가 스키마상 가장 중요한 결정 지점이다.

### 핵심 설계 결정: 문항 단위 상태 테이블 도입
현재 "극복"은 *같은 문제지를 통째로 재응시*했을 때만 갱신된다(파생 계산).
섞어풀기는 문제지 단위 응시가 아니므로, 파생만으로는 표현이 안 된다. 도입할 것:

```
review_sessions        -- 섞어풀기 세션 (user_id, 필터 조건 스냅샷, score, created_at)
review_session_items   -- 세션 문항 (session_id, question_id, selected_choice, is_correct)
user_question_status   -- 문항별 통합 상태 (user_id, question_id,
                       --   wrong_count, last_result, last_answered_at, source)
```

- `user_question_status`는 문제지 CBT 채점 시(`cbt-attempt.ts`)와 섞어풀기 채점 시
  양쪽에서 갱신한다. 오답노트 화면의 극복 판정을 이 테이블 기준으로 바꾸면
  "섞어풀기에서 맞히면 극복" 이 자연스럽게 성립한다.
- 기존 사용자 데이터는 `cbt_attempt_answers`에서 일회성 백필.
- **주의(RLS)**: 채점은 반드시 서버에서. `paper_answers`는 정답 유출 방지로
  일반 SELECT가 막혀 있으므로 섞어풀기 채점도 기존 CBT처럼 service role 경유.

### 만들 것
- 진입점: 과목 오답노트 상단 "섞어풀기 시작" 버튼 → 설정 시트
  (범위: 이 과목/전체, 미극복만 여부, 문항 수 10/20/전체, 순서 섞기).
- 풀이 화면: `cbt-solver`를 "가상 문제지"(문항 배열)를 받을 수 있게 일반화.
  문항마다 출처(문제지·번호)는 결과 화면에서만 노출(풀이 중엔 힌트가 되므로 숨김).
- 결과 화면: 맞힌 문항은 극복 처리 표시, 틀린 문항은 즉시 해설 노출.
- **엣지 케이스**: 이미지 미크롭 문항은 출제 대상에서 제외(`question_images` 존재
  검사), `voided_questions`(정답 없음 처리 문항) 제외, 5지선다/4지선다 혼재 시
  문항별 `choice_count` 사용(이미 문항 테이블에 있음).

### 완료 기준
오답 30개인 계정으로 "미극복만 20문항 섞어풀기" → 채점 → 오답노트로 돌아왔을 때
맞힌 문항에 극복 배지가 붙는 왕복 흐름 완주.

## Phase 3 — AI 약점 진단 (일 1회)

**목표**: 사용자의 오답 이력을 AI가 읽고 "무엇이 약한지 + 뭘 하면 되는지"를
하루 1회 리포트로 제공.

### 재료 (이미 있음)
- 오답 문항 × `question_explanations.keyword_title` 조인 → **틀린 개념 분포**.
  이게 이 기능의 승부처다. 해설 배치 루틴이 커버리지를 계속 넓히고 있으므로
  시간이 갈수록 진단이 정교해진다.
- 과목별 정오율·회독별 추이(`cbt_attempts.score` 시계열), 풀이 시간
  (`duration_seconds`), 반복 오답(wrong_count ≥ 2), 극복률.

### 스키마·제한
```
ai_diagnoses (user_id, diagnosis_date date, report jsonb, model, created_at,
              UNIQUE (user_id, diagnosis_date))
```
- "일 1회"는 unique 제약으로 강제 — `explanation_access_log`식 카운트보다 단순하고
  경합에도 안전. 당일 리포트가 있으면 캐시 표시, 없으면 생성 버튼 활성화.
- 리포트는 jsonb 구조화(취약 개념 top N + 근거 문항, 과목별 진단 한 줄, 추천
  액션)로 저장해 UI가 안정적으로 그리게 한다. 자유 서술 마크다운으로 받지 말 것.

### 생성 방식 결정: 온디맨드 API 호출 (권장)
| | 온디맨드 API (권장) | 야간 배치(기존 루틴식) |
|---|---|---|
| 비용 | 누른 사용자만, Haiku/Sonnet이면 회당 원 단위 | 전 활성 사용자 선생성 → 낭비 큼 |
| 신선도 | 버튼 누른 시점 데이터 | 최대 하루 지연 |
| 인프라 | 서버 액션 + API 키 1개 | 루틴 슬롯·겹침 관리 부담 추가 |

해설 배치와 달리 진단은 사용자가 요청할 때만 가치가 있으므로 온디맨드가 맞다.
입력은 원문 이미지가 아니라 **집계된 통계 + 개념 키워드 목록**(텍스트)만 넣으면
되므로 토큰이 작고, 구조화 출력(tool use)으로 받으면 파싱도 안정적이다.
단, 실비 API 과금이 새로 생기는 지점이므로 배포 전에 회당 비용 상한을 계산해 둘 것.

### 콜드 스타트 규칙
- 최소 데이터 문턱(예: 누적 오답 15개 또는 응시 3회) 미만이면 버튼 대신
  "○문제 더 풀면 진단을 받을 수 있어요" 안내 — 빈약한 데이터로 뻔한 리포트를
  주는 것이 기능 신뢰를 가장 빨리 깎는다.
- 개념 키워드가 없는 문항(해설 미생성)은 과목/문제지 수준 통계로만 반영.

### 리포트 → 행동 연결 (중요)
진단은 읽고 끝나면 안 된다. 각 취약 개념 항목에서 바로:
- "이 개념 틀린 문항 모아보기" (Phase 1 필터 딥링크)
- "이 개념만 섞어풀기" (Phase 2 프리셋 딥링크)
로 이어지게 한다. Phase 1·2가 선행돼야 하는 이유가 이것이다.

## UX 원칙 — 기능은 늘어도 표면은 늘리지 않는다

기능 4단계를 다 넣었을 때 사용자가 헷갈리는 것을 막는 장치. **혼란의 원인은
기능 개수가 아니라 진입점(메뉴·화면·버튼) 개수**다. 아래 원칙을 모든 Phase에
공통 적용한다.

### 1. 표면은 "오답노트" 하나
사용자에게 보이는 메뉴는 지금과 똑같이 오답노트 하나뿐이다. 모아보기·섞어풀기·
진단·복습은 별도 메뉴가 아니라 전부 그 안의 구성 요소다. 전체 화면 수 상한을
5개로 고정한다:

```
마이페이지 > 오답노트 (허브)
├─ ① 허브: "오늘 카드" + AI 진단 배너 + 과목 카드 목록  ← 기존 화면 확장
├─ ② 과목 상세: [문제지별 | 문항 모아보기] 탭 + 섞어풀기 버튼
├─ ③ 풀이 화면 (기존 CBT 솔버 재사용)
├─ ④ 풀이 결과
└─ ⑤ AI 진단 리포트
```

### 2. 기능 나열이 아니라 "다음 행동 하나"를 제시
허브 최상단에는 버튼 여러 개를 늘어놓지 않고, 상황에 맞는 **CTA 하나짜리
"오늘 카드"**만 둔다. 우선순위 규칙으로 자동 선택:

- 복습 예정 문항 있음 → "오늘 복습할 문항 12개 · 시작"
- 없고 미극복 오답 충분 → "미극복 24문항 섞어풀기"
- 진단 조건 충족 + 오늘 미수령 → "AI 약점 진단 받기"
- 아무것도 없음 → 최근 과목 이어보기

나머지 기능은 카드 아래·과목 상세에 평범하게 존재한다. 뭘 할지 고르게 하지
말고, 고른 결과를 보여준다.

### 3. 점진적 공개 — 데이터가 쌓여야 기능이 나타난다
신규 사용자에게 빈 진단·빈 섞어풀기를 보여주는 것이 혼란의 최대 원인이므로,
데이터 문턱 전에는 기능 자체를 렌더링하지 않는다 (회색 비활성 버튼도 두지 않음):

| 상태 | 보이는 것 |
|---|---|
| 오답 0 | 기존 오답노트 안내만 |
| 오답 1+ | 오답 목록 + 모아보기 탭 |
| 오답 ~10+ | 섞어풀기 버튼 등장 |
| 오답 ~15+ (or 응시 3회+) | AI 진단 배너 등장 |

처음 등장할 때 "새 기능" 배지 한 번이면 온보딩은 충분하다. 별도 튜토리얼을
만들지 않는다.

### 4. Phase 4는 새 기능이 아니라 기존 표면의 속성으로 흡수
Phase 4 항목들은 전용 화면·메뉴를 만드는 순간 "기능 6개짜리 앱"이 된다.
전부 기존 표면에 얹는다 — **새 화면 0개**가 Phase 4의 설계 제약이다:

- 복습 스케줄 → 허브 "오늘 카드"의 한 상태 + 섞어풀기 기본 프리셋
- 개념 태그 → 모아보기 탭의 필터 하나
- 전국 오답률 → 문항 카드의 배지 하나
- 문항 메모 → 문항 카드의 접힌 입력 필드
- PDF 내보내기 → 모아보기 탭의 인쇄 버튼
- D-day 플랜 → 진단 리포트의 확장 섹션

### 5. 설정을 노출하지 말고 기본값으로 흡수
섞어풀기 설정 시트(범위·문항 수·순서)는 첫 진입부터 펼치지 않는다. "미극복만 ·
20문항 · 섞기"를 기본값으로 즉시 시작하게 하고, 바꾸고 싶은 사용자만 "설정"을
연다. 진단도 옵션 없이 버튼 하나. 이름도 기능명("간격 반복", "진단")보다 행동
언어("다시 풀기", "약점 보기")를 쓴다.

## Phase 4 — 확장 아이디어 (우선순위 낮음, 검증 후 선별)

> 공통 제약: 위 UX 원칙 4번 — 어떤 항목도 새 화면·새 메뉴를 만들지 않고
> 기존 표면(허브 카드·모아보기 필터·문항 카드·진단 리포트)에 속성으로 얹는다.

1. **복습 스케줄(간격 반복)**: 틀린 문항을 1·3·7일 후 복습 큐에 자동 배치,
   마이페이지에 "오늘 복습할 문항 N개" 배지. `user_question_status`에
   `next_review_at`만 더하면 되므로 Phase 2 스키마 위에 얹기 쉽다. 스트릭
   (`streak.ts`)과 결합하면 재방문 동기가 강해진다.
2. **개념 태그 브라우징**: keyword_title을 과목 하위 태그처럼 노출 —
   "행정법 > 처분성" 틀린 문항 모아보기. 태그 정규화(유사 키워드 병합)가
   필요해지면 그때 AI 일괄 정리 배치를 한 번 돌린다. `unit_tag` 백필도 이때 함께.
3. **전국 오답률 통계**: `cbt_attempt_answers`를 문항별로 집계해 "응시자 68%가
   틀린 문제" 배지, "고난도만 섞어풀기" 프리셋. 익명 집계라 개인정보 부담 없음.
   응시 데이터가 충분히 쌓인 뒤에 의미가 생긴다(표본 적으면 오해만 유발).
4. **문항 메모**: 오답 카드에 사용자 메모 1필드. 구현은 얇지만 "내 노트"라는
   소유감을 만든다.
5. **오답노트 PDF 내보내기**: 시험장 직전 복습용 인쇄물. Phase 1 화면의 인쇄
   최적화로 시작해 수요 보고 전용 생성으로.
6. **D-day 학습 플랜**: 목표 시험일 등록 → 남은 기간에 미극복 문항·취약 개념을
   주 단위로 배분. AI 진단(Phase 3)의 확장판이며 가장 마지막.

## 결정 기록 — 섞어풀기 뽑기 기준 (2026-07-29, 구현 완료)

Phase 2의 섞어풀기는 `shuffle(candidates).slice(0, limit)` 로 균등 무작위였다. 오답이
30개일 때는 문제가 없지만, 반년 회독하면 수백~수천 개가 쌓인다. 그 상태에서 균등
추출은 "2번 틀린 문항"과 "반년 전 한 번 틀린 문항"을 같은 확률로 내보내, 정작
위험한 문항을 만날 확률을 계속 희석시킨다.

**채택하지 않은 안**: `2번 이상 틀린 것만` / `30일 이내만` 필터. 구현은 제일 얇지만
조건 밖 문항이 영구히 안 나온다 — 시험 준비에서 제일 위험한 게 "오래돼서 잊은
오답"인데 그게 통째로 사라진다.

**채택**: 층(tier)별 정원제. 층 안에서는 여전히 무작위라 같은 문항이 반복되지 않는다.

| 층 | 조건 | 가중 |
|---|---|---|
| A | `wrong_count >= 2` | 3 |
| B | 30일 이내에 틀림 | 2 |
| C | 나머지 미극복 | 1 |

20문항이면 A 10 · B 7 · C 3. 어느 층이 모자라면 그 자리는 위험한 층부터 메운다
(정원이 남아 20개를 못 채우는 일은 없다). 노출은 칩 2개 — `약한 문제 우선`(기본) /
`전체 랜덤` (UX 원칙 5: 설정을 노출하지 말고 기본값으로 흡수).

- 규칙 정본: `packages/core/src/review-pick.ts` (+ `review-pick.test.ts` 로 정원 고정)
- 엣지 함수 사본: `supabase/functions/_shared/review-pick.ts` — **한쪽만 고치면 웹과
  앱이 다른 문제를 낸다. 층 기준·가중치는 반드시 양쪽 함께 고칠 것.**
- 스키마 변경 없음. `user_question_status.wrong_count` / `last_answered_at` 재사용.
- 복습(간격 반복, `review-queue.ts`)과는 다른 기능이다. 복습은 `srs_due_at` 이 된
  문항만 연체 순으로 내며 무작위가 없다. 층 정원제는 "지금 아무거나 좀 풀고 싶다"를
  받는 자리라 무작위성을 없애지 않고 기울이기만 한다.
- 앱은 뽑기 방식 칩이 아직 없다(섞어풀기 진입이 곧 시작이라 설정 자리가 없음).
  엣지 함수 기본값이 `weighted` 라 기준 자체는 웹과 같다.

## 결정 기록 — 복습 과목 보류 (2026-07-29, 구현 완료)

"지금은 국어만 판다" 같은 시기에 다른 과목이 매일 큐에 섞여 들어오면 복습 자체를
안 하게 된다. 마이페이지 `ReviewDueCard` 안 접힌 줄에서 과목을 끄고 켠다
(새 화면 0개 — UX 원칙 4).

**저장은 "끈 과목"(`review_preferences.paused_subject_ids`) 목록이다.** 켠 과목을
담는 include 목록이 아닌 이유: 나중에 새로 공부를 시작한 과목이 기본으로 켜져 있어야
한다. include 목록이면 새 과목이 조용히 빠진 채로 남고, 사용자는 그걸 버그로 읽는다.

**보류 중에도 `srs_due_at` 은 건드리지 않는다.** 보류는 잠깐 안 보는 것이지 진도를
지우는 게 아니다. 대신 다시 켤 때 밀린(연체) 문항을 며칠에 걸쳐 다시 뿌린다
(`packages/core/src/review-resume.ts`, 하루 몫 10 = 큐 상한의 절반, 최대 30일).
안 하면 재개 첫날 예보 오늘 칸이 수백으로 뜨고(사용자는 고장으로 읽는다), 큐
우선순위가 연체순이라 그 과목이 하루 상한을 통째로 먹어 다른 과목이 몇 주째 안 나온다.
문항이 아주 많으면 하루 몫을 늘려서라도 30일 안에 다 밀어 넣는다 — 마지막 날에
몰아넣으면 같은 문제가 재현된다.

- 마지막 한 과목은 못 끄게 막는다(전부 끄면 복습이 통째로 멈춘다).
- 앱은 설정 UI 없이 결과만 존중한다 — 리마인더 문구의 오답 수에서 보류 과목을 뺀다
  (`apps/mobile/app/settings.tsx`). 보류 해제 쓰기는 웹 서버 경로에만 둔다
  (`user_question_status` 는 쓰기 정책이 없어 service_role 경유여야 한다).
- **적용 범위는 복습(간격 반복)까지다.** 섞어풀기는 사용자가 그 자리에서 과목을
  직접 고르는 기능이라 보류를 적용하지 않는다.
- `subject_bookmarks`(즐겨찾는 과목)를 재사용하지 않았다. 그쪽은 과목 탐색용
  바로가기라, 즐겨찾기를 지웠다고 복습이 멈추면 안 된다.

## 결정 기록 — 홈 복습 유도 모달 (2026-07-29, 구현 완료)

로그인 사용자가 홈에 들어오면 "새 문제보다 복습 먼저"를 하루 한 번 제안한다
(`review-nudge-modal.tsx`).

- **홈 서버 렌더에 복습 요약을 넣지 않았다.** 요약 계산은 이미지 조회까지 도는 무거운
  작업인데 홈은 모두가 매번 여는 화면이다. 모달이 마운트된 뒤 로컬 저장소로 "오늘
  이미 봤는지"를 먼저 보고, 안 봤을 때만 서버 액션을 부른다 — 같은 날 두 번째
  방문부터는 네트워크 비용이 0이다.
- 하루 경계는 복습 스케줄과 같은 KST 04:00(`srsDayIndex` 재사용). 자정 기준이면
  새벽 3시에 푼 사람에게 두 시간 뒤 같은 모달이 다시 뜬다.
- 띄우는 순간 "봤음"으로 기록한다. 닫기를 안 누르고 나가도 같은 날 다시 뜨면 안 된다.
- 무료 사용자에겐 뜨지 않는다(서버 액션이 0을 돌려준다). 못 누르는 걸 모달로 띄우면
  홈 자체를 피하게 된다 — `review-due-card.tsx` 가 홈에 잠긴 카드를 두지 않은 이유와 같다.
- 오늘 복습할 문항이 0이면 뜨지 않는다.

## 결정 기록 — 복습 알고리즘 재검토 (2026-08-04, 구현 완료)

간격 반복을 얹은 지 며칠 뒤 공시생 관점에서 다시 본 결과. 골격(대기 풀·하루 상한·
leech·KST 04시 경계)은 그대로 두고 네 가지를 고쳤다. **D-day(목표 시험일) 연동은
별도 작업으로 뺐다.**

### 1. 경과일을 보지 않던 스케줄 갱신 (가장 컸던 문제)

`recordQuestionResults`는 채점된 모든 문항에 `nextSrs`를 돌리는데, `nextSrs`는
"같은 날 + 정답" 말고는 시점을 보지 않았다. 그런데 이 서비스의 채점은 복습
세션에서만 일어나지 않는다 — **공시생의 기본 학습 방식이 문제지 회독**이고,
섞어풀기도 스케줄을 무시한다. 그래서 이런 일이 정상적으로 벌어졌다:

| 상황 | 예전 | 지금 |
|---|---|---|
| 간격 62일 문항을 5일 만에 회독에서 맞힘 | 62 → 174일 | 5일치만 인정(≈69일) |
| 간격 62일 문항을 5일 만에 회독에서 틀림 | 1일 리셋 + lapse + leech 진행 | 반감(31일), lapse 없음 |

두 축으로 나눠 판단한다. **오답은 "예정일이 됐나"**(`dueProgress`) — 예정일 전에
끌려 나와 틀린 건 스케줄의 실패가 아니다. **정답은 "실제로 얼마나 버텼나"**
(`retainedProgress`) — 62일 뒤로 잡아둔 걸 5일 만에 맞힌 건 5일치 기억이다.
정답 배수는 `1 + (ease − 1) × 비율`이라 비율 1이면 예전과 똑같은 × ease다.

조기 오답의 재확인(3시간 뒤)에서 또 틀리면 그때는 예정일이 지난 뒤라 정상
lapse로 처리된다 — 완화가 leech 판정을 무력화하지 않는다.

`user_question_status.srs_due_at`을 `nextSrs`에 넘겨주기만 하면 되고, 스키마 변경은
없다. dueAt을 안 주면 예전 동작 그대로라 마이그레이션 순서도 안 탄다.

### 2. 모든 정답을 Anki의 "쉬움"으로 취급하던 ease

`SRS_EASE_BONUS 0.1` / `SRS_MAX_EASE 2.8`은 SM-2에서 q=5(완벽하게 즉시 기억)일 때의
값인데, 우리 채점은 맞다/틀리다 2단계라 "겨우 맞힌 것"과 "확실히 아는 것"을 구분할
수 없다. 세 번만 맞히면 상한에 붙어 간격이 1 → 3 → 8 → 22 → 62 → 174로 뛰었다.
4지선다는 몰라도 25%, 두 개까지 좁히면 50%가 맞는다.

→ **보너스 0.05 / 상한 2.5(= 초기값)**. 정답으로는 기본값보다 후해지지 않고,
무너져 깎인 ease의 회복 전용으로만 오른다. 궤적은 1 → 3 → 8 → 20 → 50 → 125.

### 3. 큐 구성이 아니라 순서만 섞고 있던 과목 인터리빙

`interleaveBySubject`는 **뽑은 것의 순서만** 바꾼다. 행정법 due가 200개면 점수순
상위 20개가 전부 행정법이고 인터리빙은 아무 일도 못 한다. 공시는 5과목을 같은 날
보므로 한 과목 독점은 그 자체로 사고다(과목 보류 기능도 절반은 이 증상의 우회로였다).

→ 과목마다 최소 몫(`SUBJECT_MIN_SLOTS = 2`, 하루 총량에 비례)을 먼저 떼고 남은
자리는 예전처럼 위험도 경쟁. 균등 배분이 아니다 — 밀린 과목이 더 많이 나오는 건
맞는 동작이고, 막으려는 건 "국어가 며칠째 안 나옴"뿐이다.

신규 승격은 아예 과목 라운드로빈으로 간다. 승격 순서가 "자주 틀린 것 먼저"인데
1회독 중에는 전부 `wrong_count 1`로 동점이라, 그대로 두면 가장 오래전에 푼
시험지부터 순서대로 = 신규 10개가 통째로 한 과목이 된다.

### 4. 간격 fuzz

간격이 결정적이라 하루에 푼 20문항이 영원히 같은 날 함께 움직였다. 예보표의
"오늘 0, 3일 뒤 40" 같은 요철이 그 결과이고, 밀린 복습 정리·보류 해제 재분산 같은
사후 보정이 필요했던 원인 중 하나다. → 간격 4일 이상이면 ±10%(Anki와 같은 자리).

주입식(`opts.fuzz`)이라 기본은 결정적이다. `buildDueQueue`는 여전히 순수·결정적이라
"배너 숫자 = 세션 문항"이 유지된다 — 흔드는 건 쓰기 시점의 `nextSrs`뿐이다.

### 5. `srs_reviews` — 알고리즘을 검증할 수 있게 하는 로그

`user_question_status`는 "지금 상태"만 들고 있어서 **"간격 8일에서 실제 정답률이
몇 %였나"를 셀 수 없었다.** 그러면 위에서 고른 상수들(ease 2.5, 1·3일 학습 단계,
연체 점수 상한 14일, leech 8)이 맞는지 확인할 방법이 영원히 없다. 간격 반복은

## 결정 기록 — 신규 유저 시뮬레이션과 그 결론 (2026-08-04)

실제 `buildDueQueue`/`nextSrs`를 그대로 굴려 신규 유저 45일치를 돌렸다. 전제:
1일차 200문항 응시·오답 60(14/30/16), 2~14일차 매일 새 오답 40, 15일차부터 회독 종료.
복습 정답률은 처음 55%에서 통과할수록 +8%p. 총 유입 580개.

### 확인된 것 (설계대로 작동)

- 과목 최소 정원이 실제로 먹힌다. 과목2 유입이 2배인데도 과목1·3이 매일 3~8개씩
  꾸준히 나온다. 정원이 없었으면 과목2가 큐를 계속 먹었을 자리다.
- 연체가 45일 내내 13~25로 안정적이다. "오늘 20개, 끝" 감각이 유지된다.
- 예보표가 평탄하다(`20 20 15 12 12 11 12`). fuzz 효과.

### 드러난 것 — 대기 풀이 사실상 안 줄어든다

회독이 끝나 유입이 0인데도 대기 풀은 30일 동안 531 → 470, **하루 2개꼴**로만 준다.
이 속도면 470개 소화에 8개월이다. 복습 몫이 상한을 먹어 신규 몫이 자주 0이 되기 때문.

**채택하지 않은 안: 신규 몫 바닥 보장** (하루 20 중 5개는 무조건 신규).
시뮬레이션으로 반증했다 — 대기 풀은 확실히 비우지만(120일에 0) **연체가 456개로
폭발한다.** 하루 상한이 애초에 막으려던 실패 모드가 반대쪽에서 재현될 뿐이다.

| 일차 | 현재(남는 자리에만 신규) | 신규 바닥 5 | 현재 연체 | 바닥안 연체 |
|---|---|---|---|---|
| 45 | 470 | 355 | 16 | 177 |
| 120 | 359 | 0 | 22 | **456** |

**결론: 현재 설계가 옳다.** 대기 풀 정체는 버그가 아니라 용량 문제다. 하루 40개씩
새로 틀리는 속도로 회독하면서 하루 상한 20은 산술적으로 불가능한 조합이다.
45일 뒤 상태 비교(상한 60·정답률 70%면 예약 417 · 대기 161 · 연체 56로 건강해진다):

| 설정 | 예약중 | 대기풀 | 접힘 | 간격 8일+ |
|---|---|---|---|---|
| 상한 20 · 55% | 99 | 470 | 11 | 69 |
| 상한 40 · 70% | 273 | 305 | 2 | 210 |
| 상한 60 · 70% | 417 | 161 | 2 | 328 |

→ **해야 할 것은 알고리즘 수정이 아니라 안내다.** 대기 풀이 임계를 넘으면 하루
상한 상향을 권하고, 유입이 승격 능력을 크게 앞서면 "새 문제지보다 오답 먼저"를
알린다(홈 유도 모달 자리 재활용 — 새 화면 0개). 아직 미구현.

부수 발견: 정답률 55%에서 상한을 40으로 올리면 접힘이 11 → 24로 는다. 자주 만나니
자주 틀려 lapses가 빨리 쌓인다. leech 임계 8이 정답률 가정에 민감하다는 뜻이라,
`srs_reviews`가 쌓이면 실측으로 정할 것.

## 결정 기록 — 전국 정답률 기반 문항 선정 (2026-08-04, 설계만·미구현)

"정답률이 아주 높은 문항은 실수에 가까우니 빼고, 아주 낮은 문항은 지엽적이니
우선순위를 낮추자"는 방향. **지금은 구현하지 않는다** — 실사용자가 없어 표본이 0이고,
필요한 재료가 전부 원본에 남아 있어 나중에 소급 계산되기 때문이다.

| 필요한 것 | 저장됨 | 소급 |
|---|---|---|
| 첫 응시만 골라내기 | `cbt_attempts.created_at` + user_id + paper_id | ✅ |
| 미응답 제외 | `cbt_attempt_answers.selected_choice` (null 보존) | ✅ |
| 찍기 응시 제외 | `cbt_attempts.duration_seconds` | ✅ |

### 지금 집계(`paper_question_wrong_rates`)가 가진 편향 — 쓰기 전에 고칠 것

1. **회독 중복**: 모든 응시를 센다. 한 사람이 10회독하면 혼자 10표고, 2·3회차는
   정답률이 훨씬 높다. 결과적으로 "문항 난이도"가 아니라 "그 문제지를 여러 번 푼
   사람이 얼마나 많은가"를 측정한다. → **사용자별 그 문제지 최초 응시 1건만.**
2. **미응답이 오답으로 집계됨**: 채점 루프가 전 문항에 행을 만들어(`papers/actions.ts`)
   안 푼 문항이 `is_correct=false`로 들어간다. 시간이 모자라 뒤쪽을 못 푼 응시가
   **뒷번호 문항의 정답률을 체계적으로 깎는다.** → 분모에서 `selected_choice is null` 제외.
3. **3분이면 제출 가능**(`MIN_ATTEMPT_SECONDS = 180`): 찍고 넘긴 응시가 섞인다.
   → 난이도 집계에만 별도의 소요시간 하한.

### 임계값은 절대 %가 아니라 "과목별 분위수 + 절대 가드레일(AND)"

앱에서 측정될 정답률은 실제 시험 정답률과 다르다. 사용자 구성(1회독 초보 vs 시험
직전 고수)에 따라 분포 전체가 통째로 이동한다. `90%` 같은 절대값을 박아두면 실제
평균이 55%로 나올 때 걸리는 문항이 0개가 되고, 85%로 나오면 절반이 감점된다.

```
과목별로 계산한다 (영어와 한국사는 기저 정답률이 다르다).

0.6  ← (그 과목 상위 20% 쉬움)   AND  (정답률 ≥ 85%)
1.25 ← 나머지 중간 구간 = 변별 구간
0.7  ← (그 과목 하위 10% 어려움) AND  (정답률 ≤ 30%)
1.0  ← 평활 후 표본 신뢰도 부족 (판단 보류)

예외: 본인이 2번 이상 틀린 문항은 감점하지 않는다 → max(1, w)
      "쉬운데 반복해서 틀린다"는 실수가 아니라 구멍이고, 오히려 제일 급하다.
```

이 형태는 **분포가 촘촘하면 자동으로 아무 일도 안 한다.** 가정이 틀렸을 때의 실패
모드가 "과잉 개입"이 아니라 "무개입"이라, 가정으로 시작할 때 이게 제일 중요하다.

표본 처리는 하드 컷 대신 평활: `p̂ = (정답수 + k·μ) / (응답수 + k)`, k ≈ 20.
9건과 10건 사이의 절벽이 없어진다.

### 적용 위치

| 자리 | 적용 | 이유 |
|---|---|---|
| 신규 승격 순서(`byPendingPriority`) | ✅ 최대 효과 | 대기 풀이 몇 달치라 "무엇을 먼저 태우나"가 사실상 "무엇을 공부하나"를 결정한다 |
| 섞어풀기 층 정원제(`review-pick.ts`) | ✅ | 층 안의 뽑기 확률에 계수를 곱한다 |
| **복습 큐 due 우선순위(`duePriorityScore`)** | ❌ **넣지 말 것** | 이미 스케줄이 잡힌 문항은 예정일에 봐야 한다. 난이도로 미루면 간격 반복이 무의미해진다 |

- **배제가 아니라 가중이다.** "90%가 맞히는 문제를 내가 틀렸다"는 그 자체로 강한
  신호(기본기 구멍)고, 배제하면 그 문항이 대기 풀에 영원히 남아 화면의 대기 숫자가
  안 줄어든다. 섞어풀기 층 정원제와 같은 이유다("조건 밖 문항은 영구히 안 나온다").
- 집계는 매번 RPC로 돌리기엔 무겁다. `question_difficulty`(paper_id, question_number,
  first_attempts, first_correct, updated_at) 테이블을 야간 배치로 갱신하는 형태가 맞다.
- `difficulty_ratings`는 **문제지 단위 별점**이라 문항 선정에 쓸 수 없다.

**착수 조건**: 첫 응시 기준 표본 30건 이상인 문항이 의미 있는 수로 쌓였을 때.
그때 정답률 분포를 먼저 재고 위 임계를 확정할 것.

## 결정 기록 — 문항별 소요시간은 수집하지 않는다 (2026-08-04)

찍기 자동 판정("정답인데 평소보다 오래 걸림 → ease 보너스 0")과 콜드스타트 난이도
신호로 검토했으나 **수집하지 않기로 했다.**

검토 내용은 남겨 둔다. 나중에 다시 필요해지면 이 설계로 시작하면 된다:

- **절대 시간은 쓸 수 없다.** 영어 독해 3분과 한국사 단답 15초가 둘 다 정상이다.
  판정은 항상 배수로 하고, baseline은 3단계 폴백:
  ① 그 문항의 중앙값(표본 ≥ 20) → ② (과목 × `questions.passage_id` 유무) 중앙값
  → ③ 같은 세션·같은 과목 문항들의 중앙값(사용자 1명부터 작동. 읽기 속도와 그날
  컨디션이 세션 내 상수라 자동 소거된다).
- **"느리게 맞힌 정답"만 쓴다.** 찍은 문항은 오히려 빠르다 — 빠른 정답을 찍음으로
  처리하면 진짜 아는 사람을 벌준다. 느린 정답만 쓰면 방향이 명확하고, 오판해도
  손해가 "간격이 조금 덜 벌어짐"뿐이다.
- **계측의 함정이 기준보다 중요하다**: 문항 왕복(누적 체류로), 자리 비움(1회 체류
  3분 절단), 탭 비활성(`visibilitychange`로 정지), 전체보기(PDF) 모드는 측정 불가,
  첫 문항은 baseline에서 제외. 이거 없이 모으면 데이터가 통째로 쓰레기가 된다.

**비용**: 소요시간은 소급 계산이 안 되는 유일한 항목이다. 나중에 필요해지면 그
시점부터의 데이터만 쌓인다(전국 정답률과 달리 과거를 복원할 수 없다).
